Post-mortem 2026-08-17 host f · darwin ADR 0011

Two builds of one app, and neither knew about the other

The complaint was that mouse clicks felt wrong. The investigation turned up two unrelated causes: a macOS setting sitting at the fast extreme of its slider, and a Nix-managed app that had quietly floated off its pin four days earlier. This is what happened and what changed.

Cause of the symptom

Double-click window was 150 ms

com.apple.mouse.doubleClickThreshold was 0.15 against a macOS default of 0.5. Miss that window and the OS delivers two single clicks instead of a double-click. No module owned the key, so nothing put it back.

Cause of the update nagging

Sparkle rewrote the pinned bundle

BetterMouse self-updated the writable /Applications copy from build 8904 to 8905. The activation guard couldn't see it, so every later rebuild was a no-op against a bundle that no longer matched the flake.

Three sources, two answers

Every place that could report a BetterMouse version was asked. They did not agree, and the copy holding the event tap was not the copy the LaunchAgent pointed at.

Source of truth Reported What it actually is
pkgs/bettermouse.nix 1.6.8904 The pin. What the flake promises is installed.
/Applications/.bettermouse.src 8904 Marker symlink → hxbffr3xq561p50vxr7vsji2x8xvsddq. Records the source, not the result.
/Applications/BetterMouse.app 8905 Rewritten in place by Sparkle. The LaunchAgent's target.
/Applications/Nix Apps/BetterMouse.app 8904 Second copy, same bundle id. This is the one that was running.

Both bundles claim CFBundleIdentifier = com.naotanhaocan.BetterMouse, share one preferences file, and compete for one Accessibility grant.

How the pin came undone

Three defects, each harmless alone. The first created the opening, the second made it invisible, and the third cancelled the safeguard that the whole module was built around.

1

The module made the bundle writable

install_managed_app ran chmod -R u+w on the /Applications copy so a later version bump could replace it. That same write bit is exactly what Sparkle needs to update an app in place — and Sparkle was on, with SUEnableAutomaticChecks and SUAutomaticallyUpdate both set to 1, checking daily.

2

The re-copy guard compared the wrong thing

Activation decided whether to reinstall using this test:

[ ! -e "$dst" ] || [ "$(readlink "$marker" 2>/dev/null)" != "$pkg" ]

The marker tracks the source store path. It never looks at the installed bundle. After Sparkle rewrote the app, the marker still pointed at the 8904 store path and $dst still existed — so the condition was false, the re-copy was skipped, and the drift became permanent. In-place mutation is the one failure mode this guard structurally cannot detect.

3

A second copy defeated the store-path workaround

The module's central comment explains why the app is copied to /Applications at all: granting Accessibility to a store path stamps a kernel com.apple.macl xattr that makes the bundle undeletable even by root, which aborts nix.gc for the entire store.

But the package was also in environment.systemPackages, which publishes /Applications/Nix Apps/BetterMouse.app. With two bundles sharing one id, LaunchServices resolved open -g /Applications/BetterMouse.app to the store-backed copy — and that is the copy that got the Accessibility grant.

Confirmed on disk. com.apple.macl is present on /Applications/Nix Apps/BetterMouse.app. The exact breakage the module was written to prevent had already happened, caused by the module's own package list.

Why BetterMouse stops being Nix-managed

Fixing the guard would close defect 2 and leave the structural problem intact. Four properties of this app fight declarative packaging, and any one of them is disqualifying.

  • It self-updates by design. Sparkle runs with automatic check and automatic install both on. Any writable copy gets rewritten; the alternative is disabling the updater and hand-bumping a paid app built to stay current.
  • Its permissions are path-bound. An event-tap app is useless without Accessibility and Input Monitoring, those grants attach to a specific bundle path, and every version bump moves the store path.
  • Granting that permission poisons the store. com.apple.macl on a store path breaks garbage collection globally. The /Applications-copy workaround exists only to dodge this, and sits one stray systemPackages entry away from failing — as it just did.
  • There is no real release channel. No GitHub releases; the bumper scraped a WordPress RSS feed that mixes BetterMouse and thePadToo posts, and had already needed one fix for that.

So BetterMouse joins Dropbox (ADR 0005) as a deliberate exception to the pure-Nix-first policy. It is installed and updated entirely through its own GUI, and there is nothing left about it in the flake.

What changed in the repo

Deleted pkgs/bettermouse.nix The derivation and its pin.
Deleted scripts/update-bettermouse.sh The RSS-scraping version bumper.
Deleted modules/darwin/mouse-display.nix Replaced — the module no longer manages a mouse.
Added modules/darwin/display.nix martin.display, BetterDisplay only, plus one-shot cleanup of the marker and seed stamp Nix left behind.
Added docs/adr/0011-bettermouse-is-gui-managed-not-nix-managed.md The decision record this page summarizes.
Edited modules/darwin/defaults.nix Pins com.apple.mouse.doubleClickThreshold = 0.5 under CustomUserPreferences.NSGlobalDomain, with a matching entry in the settings spec table.
Edited tests/integration/*.nix Two guards: darwin-settings-no-bettermouse-agent and darwin-bettermouse-not-nix-managed. Re-adding the scaffold is a regression, not a gap.
Kept /Applications/BetterMouse.app Deliberately left on disk — it is the GUI install now, and deleting it takes the Accessibility and Input-Monitoring grants with it.
Kept Sparkle auto-update Left enabled. Updating BetterMouse is the app's own job now.

What still needs a human

  1. Run just switch. It needs interactive sudo, so it can't be driven from an agent session. That is what removes the bettermouse LaunchAgent, drops /Applications/Nix Apps/BetterMouse.app, and applies the double-click fix.
  2. Log out and back in, or reboot. The double-click threshold and the LaunchAgent change are both read at login.
  3. Open System Settings → Privacy & Security → Accessibility and Input Monitoring. Two BetterMouse entries at different paths are likely; remove them both and re-grant the one at /Applications/BetterMouse.app.
  4. If GC or activation ever fails to remove the old store-backed bundle, clear the xattr first: sudo xattr -rc "/Applications/Nix Apps/BetterMouse.app".
